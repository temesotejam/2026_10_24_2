## 1. プロジェクトの目的

本プロジェクトでは、昔のMinecraft Java Editionを参考に、見た目と操作感をできる限り忠実に再現した、無料で遊べるブラウザゲームを開発します。

特に重要なのは、Minecraftの機能を片っ端から追加することではなく、プレイヤーが「昔のMinecraftを遊んでいる」と感じられることです。

開発の基本条件

GitHub Pages

URLを開くだけでプレイ

軽量

低スペックPCにも配慮

再現性

懐かしい見た目と操作感

AI開発

追加・修正・検証を効率化

### 再現対象

基準を一つに定める必要があるため、基本方針は以下とします。

- ビジュアル・操作感：Minecraft Beta 1.7.3を主な参考対象とする。
- サバイバル機能：Minecraft Java Edition 1.2.5程度までの代表的な要素を取り入れる。
- 対象外：レッドストーン回路、マルチプレイ、最新Minecraft固有の要素。
- 公開方法：GitHub Pages上で、PC用ブラウザからシングルプレイ。

Beta時代と正式版初期では、空腹やダッシュなどの仕様が異なります。そのため、機能については初期正式版の要素を優先し、再現する仕様を個別に決めます。

### 達成したい完成状態

プレイヤーが最初にワールドを作成し、木を切り、作業台を作り、石や鉄を採掘し、家を建て、夜のモンスターと戦い、洞窟を探索してダイヤモンドを見つける。

その一連のサバイバル体験を、インストール不要のブラウザゲームで再現することを完成目標とします。

## 2. 技術構成

現段階では、[Vincent-P-essy/minecraft-clone](https://github.com/Vincent-P-essy/minecraft-clone?utm_source=chatgpt.com) を第一候補とします。

このプロジェクトには、Three.js、TypeScript、チャンク生成用Web Worker、Greedy Meshing、衝突判定、地形の自動生成、GitHub Pagesへの公開環境が存在します。MITライセンスで公開されており、改造・再配布の基盤として利用できます。

[image](https://www.google.com/s2/favicons?domain=https://github.com&sz=32)

GitHub

| 描画     | Three.js + WebGL2                         |
| -------- | ----------------------------------------- |
| 開発言語 | TypeScript                                |
| ビルド   | Vite                                      |
| 地形生成 | Seedベースのチャンク生成                  |
| 並列処理 | Web Workers                               |
| セーブ   | IndexedDB中心                             |
| テスト   | 単体テスト + Playwright等のブラウザテスト |
| 公開     | GitHub Actions → GitHub Pages             |

IndexedDBや追加のテスト環境は本プロジェクトで新規実装する想定です。

既存コードをそのまま採用することは確定せず、最初に性能・保守性・ライセンス・拡張性を評価します。

### Phase 0：基盤の検証・GitHub Pages公開

目安：8〜15時間

最初に行うのは、ゲームへの機能追加ではなく、土台が開発に耐えるかどうかの確認です。

実施内容

1. 第一候補のリポジトリを取得し、依存関係とライセンスを確認。
2. ローカルでビルドし、既存の216件の単体テストとブラウザ動作テストを実行。
3. 第二候補との性能比較を行い、開発基盤を最終選定。
4. GitHub上に自分の開発リポジトリを用意。
5. GitHub Actionsで自動ビルド・テスト・Pages公開を構築。
6. 性能測定用のFPS・フレーム時間・チャンク数・メモリ表示機能を開発用モードに追加。

完了条件： 自分のGitHub PagesのURLでワールドを開き、歩く、ジャンプする、ブロックを壊す、置くという操作ができること。ビルドとテストが正常に通ること。

### Phase 1：見た目・操作感の忠実化

目安：25〜50時間

このフェーズを最も重視します。最初に「遊んで気持ちがいい」状態を作ります。

操作の実装

| 操作            | 仕様                             |
| --------------- | -------------------------------- |
| W/A/S/D         | 前後左右移動                     |
| マウス          | 一人称視点                       |
| 左クリック      | ブロック採掘・攻撃               |
| 右クリック      | ブロック設置・使用               |
| Space           | ジャンプ                         |
| Shift           | しゃがみ                         |
| Ctrl            | ダッシュ（初期正式版寄りの追加） |
| E               | インベントリ                     |
| 1〜9 / ホイール | ホットバー切替                   |
| Esc             | メニュー・カーソル解放           |
| F5              | 三人称視点（後半に実装）         |

ベースゲームではShiftにダッシュが割り当てられているため、Minecraft風の操作へ変更します。

物理演算の調整

- 歩行速度、加速・減速
- ジャンプ速度、重力、滞空時間
- 空中での方向制御
- ブロック衝突判定
- しゃがみ時の落下防止
- 水中での浮力と移動
- 段差の乗り越え
- 視点の高さ、FOV、視点の揺れ

時間に依存して挙動が変わらないよう、物理更新には固定時間ステップを採用します。FPSが30と60で異なっても、移動距離やジャンプ高さがほぼ同じになることを確認します。

見た目の調整

16×16の独自テクスチャ、ブロックの陰影、空の色、太陽・月、雲、霧、選択ブロックの枠、手に持つアイテム、ホットバー、照準、体力・空腹ゲージを作ります。

描画を軽くするため、高解像度テクスチャ、影のリアルタイム計算、PBRなどの高度な表現は使いません。

完了条件： クリエイティブ相当の状態で10分間、自由に建築・移動できること。基準となるMinecraftの動画と並べて、操作や画面構成の大きな違いがないこと。

### Phase 2：ワールド生成・洞窟・光源

目安：20〜40時間

ベースゲームの自動生成を活用し、地形と地下探索の再現性を上げます。

地形

- 草原、森林、砂漠、雪原、山岳、海
- オーク、シラカバなどの樹木
- 地表の砂・土・石
- 洞窟、地下空洞
- 石炭、鉄、金、ダイヤモンドなどの鉱石
- ベッドロックとワールド高さ制限

地形の生成はSeed値から決定的に行い、同じSeedなら同じ地形になる構成にします。ただし、Minecraftと同じSeedから同じ地形になることまでは求めません。

光源処理

現在の第一候補には、松明や太陽光の伝播計算がありません。

[image](https://www.google.com/s2/favicons?domain=https://github.com&sz=32)

GitHub

これは洞窟探索の雰囲気に直結するため、優先度を高くします。

- 太陽光レベルの伝播
- 松明による周辺照明
- 洞窟内の暗さ
- 昼夜に伴う明るさの変化
- ブロック追加・削除時の光源更新

光源を追加すると負荷が増えるため、チャンク内の光量データを保持し、変更された範囲だけを更新する構成にします。

完了条件： 地上を長距離探索しても地形の継ぎ目が目立たず、松明を置いた洞窟で周囲が明るくなること。採掘による地形変更が再読み込み後も保持されること。

### Phase 3：アイテム・採掘・クラフト

目安：25〜50時間

ここから本格的なサバイバルゲームとしての機能を追加します。

基本システム

- ブロック破壊時のアイテムドロップ
- アイテム取得とスタック
- 36スロット相当の所持品管理
- ドラッグ＆ドロップ操作
- 2×2クラフトと3×3作業台
- 木・石・鉄・金・ダイヤの道具
- 採掘速度・適正道具・耐久値
- かまどの燃料・精錬
- チェストへの保管

最初は序盤サバイバルに必要なレシピを優先します。レシピはコードに直接大量記述せず、データファイルで管理します。

完了条件： 初期所持品ゼロの状態から、木材を採取し、作業台を作り、木のツルハシから石・鉄の道具へ進めること。

### Phase 4：サバイバル・ゲーム進行

目安：25〜50時間

実装対象

- ハートによる体力表示
- 空腹ゲージ
- 自然回復・ダメージ
- 落下・窒息・溺水・炎・溶岩
- 食料・調理・回復
- 水泳・水中呼吸
- ベッド・睡眠・スポーン地点
- 死亡・アイテム落下・リスポーン
- 小麦栽培、苗木の成長、簡単な農業

水や溶岩については、最初からMinecraftと同等の流体シミュレーションを実装するのではなく、限定的な伝播・更新処理から始めます。流体処理は軽量化との両立が難しい領域です。

完了条件： 食料を確保しながら複数日生存でき、死亡・復活・セーブによってゲーム進行が破綻しないこと。

### Phase 5：モブ・戦闘・生態系

目安：25〜50時間

初期実装するモブ

| 種類   | モブ                 | 主な動作                   |
| ------ | -------------------- | -------------------------- |
| 友好   | 豚・牛・羊・鶏       | 徘徊・逃走・繁殖・ドロップ |
| 敵対   | ゾンビ               | プレイヤー追跡・近接攻撃   |
| 敵対   | スケルトン           | 距離を保って遠距離攻撃     |
| 敵対   | クリーパー相当       | 接近後の爆発攻撃           |
| 敵対   | クモ                 | 接近・攻撃                 |
| その他 | アイテムエンティティ | 落下・滞留・回収           |

公開時の知的財産権への配慮から、モデルやテクスチャは独自に作成します。

AI処理の軽量化

近くのモブだけを高頻度で更新し、遠方のモブは低頻度更新または休止します。経路探索も全モブで毎フレーム実行せず、距離と状況に応じて頻度を変えます。

完了条件： 夜間に敵がスポーンし、逃走・戦闘・食料確保が成立すること。複数のモブがいる状態でも、極端なFPS低下や異常な経路探索が起こらないこと。

### Phase 6：セーブ・負荷対策・安定化

目安：15〜25時間

既存のlocalStorage保存から、IndexedDBを中心とした保存構造へ段階的に移行します。

保存対象は、Seed、地形変更、プレイヤー位置、インベントリ、体力・空腹、ゲーム時間、設置チェストなどです。

重要なのは、ワールド全体を保存しないことです。地形をSeedから再生成し、変更したブロックと追加状態だけ保存します。

ただし、アイテム・チェスト・モブなどの追加要素に応じて、必要な状態は確実に保存します。

完了条件： 長時間プレイ後にブラウザを閉じても続きから再開できること。セーブ失敗時に既存データが壊れないこと。バックアップを書き出せること。

### Phase 7：総合テスト・正式公開

目安：17〜30時間

- 30分・2時間以上のプレイ検証
- 複数Seedでのワールド生成
- ワールド保存・復元の反復試験
- 低性能PCを想定した描画設定の評価
- ワールド境界・大量採掘・大量アイテムの試験
- ブラウザ更新と再読込の確認
- 公開アセットのライセンス監査
- GitHub Pagesの最終動作確認

完了条件： 主要なサバイバル進行を最初から最後まで実施でき、重大な停止・データ消失がないこと。

このゲームの最重要要件の一つです。

単に軽くするのではなく、Minecraftらしい見た目を維持しながら、処理量を削減することを目指します。

上記は採用前の暫定目標であり、保証値ではありません。評価端末・画面解像度・視界距離を固定してから正式な合否基準にします。

### 具体的な軽量化方法

| 項目         | 実装方針                                    |
| ------------ | ------------------------------------------- |
| チャンク     | 16×16を基本とし、高さ方向は必要に応じて分割 |
| 描画         | Greedy Meshing・不可視面除去                |
| 地形生成     | Web Workerで並列化                          |
| 視界距離     | 4〜12チャンク程度で調整可能にする           |
| テクスチャ   | 16×16のアトラス／テクスチャ配列             |
| モブ         | 距離別の更新頻度を設定                      |
| 光源         | 変更箇所周辺だけ再計算                      |
| ワールド保存 | Seed＋差分保存                              |
| 描画解像度   | 自動・手動切替                              |
| 開発用監視   | FPS・フレーム時間・メモリ・チャンク数       |

チャンク構成などは既存実装に合わせて調整します。数値は現時点での設計候補です。

## 8. Minecraftとの再現度を検証する方法

再現度の評価は3種類に分けます。

視覚比較

同じような地形・視点・時刻の画像を比較し、UI位置、画角、ブロックの見え方、空や霧の表現を検証する。

物理・操作の数値比較

一定時間の移動距離、ジャンプ最高点、滞空時間、落下速度、衝突判定などを基準バージョンと比較する。

ゲーム進行テスト

木の採取から鉄装備の作成までを一連のテストシナリオとして実行し、サバイバルが成立するか確認する。

見た目の完全一致は、著作権上の制約もあるため保証できません。Minecraft公式はゲームのテクスチャ、モデル、音声、ソフトウェアなどの再配布について制限を設けています。公開作品では、適切な権利を持つ独自素材を使用します。

## 9. リスクと対策

| 想定リスク                   | 対策                                                         |
| ---------------------------- | ------------------------------------------------------------ |
| 機能追加でFPSが低下          | PRごとに性能比較、描画負荷の予算を設定                       |
| ブラウザ保存データの消失     | 定期保存・バックアップ・エクスポート                         |
| スマートフォンで操作しにくい | 初期はPC中心、タッチ操作は後から最適化                       |
| ワールド生成が重い           | ワーカー化・チャンク読み込み制御                             |
| ゲームが際限なく複雑化       | 基本サバイバルの完成まで機能を凍結                           |
| 著作権・ライセンス問題       | Minecraftの元アセットを使わず、独自素材と利用可能なOSSを使用 |
| AIによる不具合混入           | 自動テスト・PRレビュー・安定版タグ                           |

GitHub Pagesは通常の小規模な公開用途には十分ですが、公開サイトのサイズ上限や帯域幅の目安があるため、アセットは極力小さく保ちます。

## 結論

このプロジェクトで最も重要なのは、次の順番です。

① GitHub Pagesで動く軽量な基盤 → ② 昔のMinecraftらしい操作感と見た目 → ③ 採掘・クラフト → ④ サバイバルとモブ → ⑤ 長時間遊べる安定性。

開発規模は小さくありませんが、ゼロから作るのではなく既存のWeb向けエンジンを活用するため、AIとの共同開発に向いています。

特に今回は、最初のM1（クラシック操作版）の完成度を高くすることを重視したいです。ここで操作感や描画性能が十分に仕上がれば、その後に機能を増やしてもMinecraftらしさを維持しやすくなります。

計画書としてはこの内容を初期仕様に据え、次は実際の候補リポジトリをコードレベルで調査し、既存機能と追加機能をファイル単位で対応づけた実装設計へ進むのが適切です。
